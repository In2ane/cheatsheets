по всем трём сразу.

## Часть 1. Два типа нагрузки: OLTP и OLAP

### Термины

- **Транзакционная нагрузка, OLTP** (OnLine Transaction Processing — оперативная обработка
  транзакций) — поток мелких операций от пользователей приложения: создать заказ, обновить
  профиль, показать корзину. Каждая операция трогает **единицы строк**, но их **много**
  и ответ нужен за миллисекунды.
- **Аналитическая нагрузка, OLAP** (OnLine Analytical Processing — оперативная аналитическая
  обработка) — редкие тяжёлые запросы от аналитиков и отчётов: «выручка по регионам по месяцам
  за три года». Каждый запрос читает **миллионы строк**, но по нескольким столбцам, и секунды
  на ответ — нормально.

> Слово «online» в обоих терминах историческое: оно значит «интерактивно, в ответ на запрос»,
> в противоположность batch-обработке по расписанию. Оно **не** про интернет.

### Сравнение по осям

| Ось | OLTP | OLAP |
|---|---|---|
| Кто обращается | конечный пользователь через приложение | аналитик, BI-дашборд, отчёт |
| Строк на запрос | единицы | миллионы |
| Столбцов на запрос | вся строка целиком | 2–5 из сотни |
| Соотношение | много записи и точечного чтения | почти только чтение, запись пачками |
| Требование | латентность (мс) | пропускная способность |
| Данные | текущее состояние | история, в том числе давняя |
| Актуальность | строго сейчас | вчерашние данные обычно годятся |
| Объём | десятки ГБ – единицы ТБ | ТБ – ПБ |
| Схема | нормализованная | денормализованная, «звезда» |
| Хранение | построчное | поколоночное |
| Типичный инструмент | PostgreSQL, MySQL | ClickHouse, BigQuery, Snowflake |

### Почему одна база плохо тянет и то и другое

Дело не в «мощности сервера», а в физике хранения на диске.

**Построчное хранение (row-oriented).** Строка лежит на диске целиком, поля подряд:

```
[1|Иван|ivan@x.ru|2024-01-05|1500] [2|Ольга|olga@x.ru|2024-01-06|2300] ...
```

Прочитать одну строку целиком = одно обращение к диску. Идеально для OLTP.
Но посчитать `SUM(сумма)` по миллиону строк — значит поднять с диска **все** столбцы
миллиона строк, включая имена и адреса, которые запросу не нужны.

**Поколоночное хранение (column-oriented).** Каждый столбец — отдельный непрерывный массив:

```
id:    [1, 2, 3, ...]
имя:   [Иван, Ольга, ...]
сумма: [1500, 2300, ...]
```

`SUM(сумма)` читает ровно один массив. Плюс однотипные значения рядом жмутся в разы
(повторы, дельта-кодирование), и обрабатываются пачками через векторные инструкции процессора.
Зато «дай мне заказ №42 целиком» = собрать его из ста разных мест, а `UPDATE` одной строки —
дорогая операция во всех ста массивах.

Отсюда правило: **быстрое чтение строки и быстрая агрегация столбца — взаимоисключающие
оптимизации.** Никакой настройкой это не примиряется.

Есть и второй, организационный аргумент: тяжёлый отчёт, запущенный по боевой базе,
съедает её дисковый ввод-вывод и кэш в памяти, и пользователи в этот момент видят тормоза.
Аналитику отселяют хотя бы поэтому.

### Как их разделяют на практике

Порядок эскалации — от дешёвого к дорогому. Прыгать сразу в конец не нужно.

1. **Ничего не делать.** Пока данных мало (условно до десятков миллионов строк) и отчётов
   немного — считать аналитику прямо в PostgreSQL. Это абсолютно нормально.
2. **Реплика на чтение.** Копия боевой базы, куда идут только отчёты. Пользователей больше
   не задевает. Дёшево и решает 80 % случаев.
   > **Реплика** — копия базы на другом сервере, автоматически повторяющая изменения оригинала.
3. **Отдельное аналитическое хранилище.** Данные периодически перекладываются в ClickHouse
   или BigQuery в удобной для аналитики форме.

> **ETL** (Extract, Transform, Load) — процесс перекладывания: извлечь из источников,
> преобразовать, загрузить в хранилище. **ELT** — тот же процесс, но преобразование делается
> уже внутри хранилища, после загрузки сырых данных; так сейчас чаще.
>
> **DWH** (Data Warehouse, хранилище данных) — база, куда сведена аналитика со всей компании,
> в единой очищенной структуре.
> **Data Lake (озеро данных)** — свалка сырых файлов «как есть», структуру которым придают
> в момент чтения (тот самый schema-on-read из порции 1).
> **Витрина (data mart)** — небольшой срез хранилища под конкретный отдел или дашборд.

### Схема «звезда»

В OLAP схему специально **денормализуют** — то есть сознательно дублируют данные, чтобы
не делать соединений. Классическая форма — звезда:

- **Таблица фактов** в центре: события с числовыми мерами. Одна строка = одна продажа:
  `дата_id, товар_id, магазин_id, количество, сумма`. Она огромная и только растёт.
- **Таблицы измерений** по краям: справочники, описывающие факты — товары, магазины, даты.
  Маленькие и почти не меняются.

Запрос «выручка по категориям товаров за квартал» = один проход по фактам плюс подстановка
из мелких измерений. В нормализованной OLTP-схеме это было бы соединение шести таблиц.

> **HTAP** (Hybrid Transactional/Analytical Processing) — попытка совместить оба режима
> в одном движке (SingleStore, TiDB, отчасти Oracle In-Memory). Маркетингово популярно,
> на практике обычно проигрывает специализированным решениям на своём поле.

## Часть 2. ACID

Это набор гарантий, которые СУБД даёт транзакции. Аббревиатура придумана в 1983 году
(Хэрдер и Ройтер) и с тех пор — общий словарь индустрии.

Напомню определение из порции 1: **транзакция** — группа операций, выполняемая как единое целое.
Классический пример — перевод денег:

```sql
BEGIN;                                                        -- начали транзакцию
UPDATE accounts SET balance = balance - 100 WHERE id = 1;      -- сняли
UPDATE accounts SET balance = balance + 100 WHERE id = 2;      -- начислили
COMMIT;                                                        -- зафиксировали
```

### A — Atomicity (атомарность)

**Определение.** Транзакция применяется либо целиком, либо никак. Промежуточного состояния
«деньги сняли, но не начислили» после сбоя не остаётся.

Если между двумя `UPDATE` сервер упал, при следующем старте СУБД **откатит** незавершённую
транзакцию. Откат возможен и явно — командой `ROLLBACK`.

> Слово выбрано неудачно: «атомарность» здесь **не** про «неделимость во времени» и не про
> изоляцию от других транзакций (это буква I). Только про «всё или ничего». Точнее было бы
> «прерываемость» — abortability.

**Кто обеспечивает:** журнал (WAL, см. порцию 3) и механизм отката.

### C — Consistency (согласованность)

**Определение.** Транзакция переводит базу из одного корректного состояния в другое корректное.
Корректность определяется правилами: ограничениями схемы (`FOREIGN KEY`, `CHECK`, `UNIQUE`,
`NOT NULL`) и логикой предметной области.

Часть правил СУБД проверяет сама и не даст закоммитить их нарушение: заказ с несуществующим
`user_id` не запишется. Но правило «сумма денег в системе постоянна» база не знает — его
обеспечивает **разработчик**, правильно написав транзакцию.

> Это единственная буква в ACID, ответственность за которую лежит на приложении, а не только
> на СУБД. Многие (в том числе Мартин Клеппман в «Designing Data-Intensive Applications»)
> считают, что C попала в аббревиатуру ради красивого слова. Знать это полезно — на собеседовании
> вопрос «какая буква ACID не про базу?» встречается.
>
> Не путать с **consistency из теоремы CAP** — там это совсем другое понятие (см. часть 4).

### I — Isolation (изолированность)

**Определение.** Параллельно выполняющиеся транзакции не видят промежуточных состояний
друг друга. Идеал — как будто они выполнялись по очереди, одна за другой.

Именно эта буква лечит потерянное обновление из порции 1. Без изоляции возникают **аномалии**:

- **Грязное чтение (dirty read)** — прочитали то, что другая транзакция записала, но ещё
  не закоммитила. Она откатилась — мы работали с данными, которых никогда не существовало.
- **Неповторяющееся чтение (non-repeatable read)** — прочитали строку дважды в одной
  транзакции и получили разные значения: между чтениями кто-то её закоммитил.
- **Фантомное чтение (phantom read)** — повторили тот же `SELECT` с условием и получили
  **новые строки**, которых в первый раз не было.

Полная изоляция дорога, поэтому существуют **уровни изоляции** — компромисс между строгостью
и скоростью. Их четыре в стандарте SQL: Read Uncommitted, Read Committed, Repeatable Read,
Serializable. По умолчанию в PostgreSQL — Read Committed.

> Подробный разбор аномалий и уровней — раздел 3 роадмапа. Здесь достаточно знать,
> что **изоляция по умолчанию не полная**, и это осознанный компромисс, а не недоработка.

**Кто обеспечивает:** блокировки и/или MVCC (многоверсионность — в PostgreSQL каждая
транзакция видит свой снимок данных).

### D — Durability (долговечность)

**Определение.** Если сервер ответил «зафиксировано», данные переживут падение процесса,
перезагрузку и отключение питания. Не потеряются.

Достигается тем, что при `COMMIT` изменения гарантированно попадают на энергонезависимый
носитель — на диск, не в кэш ОС. Обычно это запись в WAL и вызов `fsync`, физически
сбрасывающий буферы на устройство.

> Абсолютной durability не бывает: диск может умереть целиком, дата-центр — сгореть.
> Поэтому реальная долговечность — это ещё и репликация на другие машины плюс бэкапы.
> Существует и настраиваемая нестрогая durability (`synchronous_commit = off` в PostgreSQL):
> отвечаем клиенту сразу, на диск сбрасываем чуть позже. Быстрее, но при отключении питания
> теряются последние доли секунды подтверждённых транзакций. Иногда это приемлемая цена.

### Кто даёт ACID

Полный ACID: PostgreSQL, MySQL (движок InnoDB), Oracle, MS SQL, SQLite.
Частично или на уровне одного документа: MongoDB (с версии 4.0 есть и многодокументные
транзакции), Redis (транзакции есть, но без отката отдельных команд).
Практически нет: Cassandra, Elasticsearch.

## Часть 3. BASE

Альтернативный набор свойств, придуманный как противопоставление ACID для распределённых
систем, где строгие гарантии слишком дороги. Аббревиатура нарочито шуточная:
ACID (кислота) против BASE (щёлочь).

- **BA — Basically Available (базово доступна).** Система отвечает на любой запрос всегда —
  пусть неактуальными данными или приблизительным ответом, но отвечает. Отказ обслуживания
  считается худшим злом, чем неточность.
- **S — Soft state (гибкое состояние).** Состояние системы может меняться само по себе,
  без новых записей извне, — за счёт распространения изменений между узлами.
- **E — Eventually consistent (согласована в конечном счёте).** Если запись прекратилась,
  через какое-то время все узлы придут к одинаковым данным. Гарантируется, что придут;
  не гарантируется, когда.

> **Eventual consistency (согласованность в конечном счёте)** — ключевое понятие всего
> распределённого мира. Записали в один узел, читаем из другого — можем какое-то время
> (миллисекунды, иногда секунды) видеть старое значение. Это не баг, а заявленное поведение.

Практический пример: счётчик просмотров видео. Разные пользователи видят слегка разные числа,
через полминуты они сходятся. Никого это не беспокоит. А вот баланс счёта так вести нельзя.

> BASE — не стандарт и не формальная модель, а публицистический ярлык. Формулировки у разных
> авторов гуляют. Знать нужно ради словаря и собеседований; строить на нём рассуждения — нет.
> Реальный водораздел проходит по CAP и по конкретным уровням согласованности.

## Часть 4. Теорема CAP

Сформулирована Эриком Брюером в 2000-м, доказана Гилбертом и Линчем в 2002-м.
Касается только **распределённых** систем — то есть данных, размазанных по нескольким узлам.
К одиночной PostgreSQL на одном сервере она не применяется вообще.

### Три буквы

- **C — Consistency (согласованность, здесь — линеаризуемость).** Любое чтение возвращает
  результат самой последней завершённой записи. Система ведёт себя так, будто копия одна,
  хотя их несколько.
  > Ещё раз: это **не** буква C из ACID. Совпадение слов — историческая неудача.
- **A — Availability (доступность).** Каждый запрос к живому узлу получает осмысленный ответ
  (не ошибку и не таймаут). Про скорость ответа речи нет.
- **P — Partition tolerance (устойчивость к разделению сети).** Система продолжает работать,
  когда сеть между узлами порвалась и они не могут обмениваться сообщениями.
  > **Network partition (сетевое разделение, split-brain)** — узлы живы, но не видят друг друга.
  > Каждая половина считает, что вторая умерла.

### Формулировка

> При возникновении сетевого разделения система вынуждена выбрать: остаться **согласованной**
> или остаться **доступной**. Обе гарантии одновременно недостижимы.

Почему — на пальцах. Узлы A и B, между ними разрыв. Клиент пишет новое значение в A.
Другой клиент читает из B. У B двух вариантов:

- ответить старым значением → нарушена **C**, сохранена **A**;
- отказаться отвечать, пока не свяжется с A → сохранена **C**, нарушена **A**.

Третьего нет. Ответить правильно B физически не может — он не знает, что произошло у A.

### Главное заблуждение

Формулировка «выбери любые два из трёх» — популярная и **неверная**. Разделение сети
не выбирают: кабели рвутся, коммутаторы виснут, дата-центры отваливаются. P — это не опция,
а факт окружающей среды.

Правильная формулировка: **выбор возникает только во время разделения, и он между C и A.**
Пока сеть цела, система спокойно даёт и то и другое.

«CA-системы» из старых картинок — это просто нераспределённые системы, то есть одиночная
база. К ним теорема не применяется.

### Как это выглядит у конкретных СУБД

**CP (жертвуем доступностью).** Меньшинство узлов при разделении перестаёт обслуживать
запросы, чтобы не выдать устаревшие данные. Так работают системы на кворумных алгоритмах
консенсуса (Raft, Paxos): пишем только если большинство узлов подтвердило.
*Примеры:* etcd, ZooKeeper, Consul, HBase, MongoDB в конфигурации по умолчанию,
распределённые SQL вроде CockroachDB и YDB.
*Уместно, когда:* цена неверных данных выше цены простоя — конфигурация кластера, блокировки,
деньги, остатки на складе.

**AP (жертвуем согласованностью).** Отвечают все узлы всегда, расхождения улаживаются потом.
*Примеры:* Cassandra, DynamoDB, Riak, CouchDB, DNS.
*Уместно, когда:* простой дороже расхождения — корзины, лента, счётчики, кэш, телеметрия.

> В Cassandra и DynamoDB выбор настраивается **на уровне отдельного запроса** через
> **кворум**: если число подтверждающих узлов при записи (W) плюс при чтении (R) больше
> общего числа реплик (N), то есть **R + W > N**, чтение гарантированно увидит последнюю
> запись. Хочешь строже — плати задержкой. Так что «CP или AP» — характеристика не столько
> продукта, сколько конкретной настройки.

### PACELC — уточнение теоремы

CAP молчит о том, что происходит, когда сеть в порядке, — а это 99.9 % времени.
Дополнение Дэниела Абади (2010):

> **if (P)artition → choose (A)vailability or (C)onsistency; (E)lse → choose (L)atency or (C)onsistency**
>
> При разделении выбирай между доступностью и согласованностью; **иначе** — между
> задержкой и согласованностью.

Смысл второй половины: даже в исправной сети согласованность стоит времени. Дождаться
подтверждения от реплик в другом дата-центре — это десятки миллисекунд на каждую запись.
Не ждать — быстро, но кто-то прочитает устаревшее.

Классификация: Cassandra и DynamoDB — **PA/EL** (всегда за скорость и доступность),
etcd и CockroachDB — **PC/EC** (всегда за согласованность), MongoDB — **PC/EC** с возможностью
настроить чтение с реплик и стать EL.

## Грабли и мифы

- **«Consistency в ACID и в CAP — одно и то же».** Разные вещи. В ACID — соблюдение правил
  целостности данных. В CAP — то, что все узлы показывают одинаковую актуальную картину.
  Самая частая путаница в теме.
- **«Выбери два из трёх».** Нет: P обязательна для распределённой системы, выбор идёт
  между C и A и только в момент разрыва сети.
- **«NoSQL не умеет ACID».** Умеет: MongoDB с 4.0, FoundationDB, CockroachDB, YugabyteDB.
  Граница проходит не по SQL/NoSQL, а по распределённости и цене гарантий.
- **«Раз есть ACID, транзакции полностью изолированы».** По умолчанию нет: Read Committed
  допускает и неповторяющееся, и фантомное чтение. Полную изоляцию надо просить явно.
- **«OLAP — это про большие данные, нам рано».** OLAP — это про **тип запросов**, а не объём.
  Отчёт по 100 тысячам строк — уже аналитическая нагрузка по характеру.
- **«Перенесём аналитику в ClickHouse и заживём».** Появляется второй источник правды,
  задержка синхронизации и целый ETL-конвейер, который надо поддерживать. Сначала — реплика.
- **«Eventually consistent = ненадёжно».** Это выбранный компромисс, а не дефект. Вопрос
  один: приемлемо ли для конкретных данных увидеть значение секундной давности.
